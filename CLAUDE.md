# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

`arco-make` (package `arcomake`, Python ≥ 3.13) builds Analysis-Ready Cloud-Optimized (ARCO) Zarr timeseries from heterogeneous sources (Copernicus Marine, Climate Data Store / Early Warning Data Store, remote NetCDF over HTTP, Zarr on GCS/S3). Every command is driven by a TOML "recipe" plus CLI arguments. It was built to produce ARCO-OCEAN; the reference recipe lives in the external `inogs/arco-ocean` repo under `configs/download/`.

## Commands

```bash
uv sync --frozen --extra dev                    # dev tools: pytest, ruff, ty, reuse, pre-commit
uv run --frozen pytest -q                       # offline test suite (synthetic data, no credentials)
uv run --frozen pytest tests/test_cli.py -k blocks   # a single test
uv run --frozen ruff check && uv run --frozen ruff format --check
uv run --frozen ty check                        # all ty rules are errors
uv run --frozen pre-commit run --all-files      # ruff, ty, reuse lint, gitleaks
uv run arco-make --help                         # CLI entry point (arcomake:cli)
```

Tests live in `tests/`: synthetic fixtures in `conftest.py` (grid with a coastline and slope, Feb 29 crossed), sample recipes in `tests/data/` (rendered with `@SOURCES@` replaced), and CLI end-to-end runs via click's `CliRunner`. Known bugs are pinned as `xfail(strict=True)`; the commit fixing a bug removes its marker. `process` and `compute-climatology` default to `--dask-setup mpi`: pass `threads` in tests.

CI (`.github/workflows/ci.yml`): lint, reuse, gitleaks secret scan, tests with a coverage gate of 80 %, on Python 3.13 as in the image. CI never downloads data or uses credentials, by design: the repository and its Actions logs are public, and pull-request code would run with the secrets. Checks against the live services are in `tests/live/` (marker `network`, skipped unless pytest gets `--live`): one tiny recipe per backend, checked for structure and plausible values. `.github/workflows/live-services.yml` runs them weekly, on demand and after merges touching the backends or `uv.lock`, never on pull requests, with the secrets of the `live-services` environment, each backend getting only its own. Locally: `uv run --frozen --extra dev --extra live pytest --live tests/live` with the credentials in the environment or the services' credential files (the `live` extra adds `eccodeslib`, an ecCodes build recent enough for GloFAS GRIB). The Apptainer image (`apptainer-build-deploy.yml`) is built on pull requests and pushed as `:latest` only from master.

Code style: **2-space indentation**, line length 100 (ruff config in `pyproject.toml`). Files start with an SPDX MIT header.

## CLI subcommands

Registered in `src/arcomake/__init__.py`: `download`, `process`, `compute-climatology` (from `climatology.py`), `validate`, and `steps` (prints the step reference). Each data command has a Pydantic config model (`DownloadConfig`, `ProcessConfig`, `ClimatologyConfig`, `ValidateConfig`) loaded via `cli_utils.read_configs(path, schema=..., inject=...)`; CLI options like `--start/--end` are injected into the parsed TOML before validation, and the output check runs after (it uses `[save] storage_options`). Checkpointing is configured as `[datasets.<name>.checkpointing]` with `step` and optional `compressors`.

**Documentation is tested:** `docs/steps.md` must equal `arco-make steps` (regenerate with `uv run arco-make steps > docs/steps.md` after changing a step or its docstring), every TOML example in a step docstring must validate, and the README recipe must load as a `DownloadConfig`. `docs/coarsen-ocean-datasets.md` (how ocean datasets are coarsened: sea fraction, fills, sea ice, river outlets) is a doctest: ```` ```pycon ```` blocks run offline (`tests/test_coarsening_notes.py`), ```` ```pycon live ```` blocks with the live checks; its global figures come from `docs/coarsen_analysis.py` (`measure RES OUT.json`, then `tables`), run by hand with credentials.

## Architecture

**Download pipeline** (`download.py` → `dataset_utils.py`): the recipe's `[start, end)` range is split into `step`-sized intervals (`datetime_utils.IterableDateInterval`). For each interval, every dataset in `datasets` is produced by `maybe_checkpointing_download_and_process`: each `part` is opened with `open_input(**part_conf)` without chunks (`xr.open_dataset`; with zarr 3 a failed chunk read of a Zarr source raises instead of becoming NaN, N8, as `tests/test_read_errors.py` checks for sources in both formats; the `[read]` tables use the same), moved by the part's `time_offset` if any (`PartTimeOffset`, e.g. `-1h` for ERA5 accumulations stamped at the end of their hour; backends that take a time range get it shifted the other way), given request timeouts (`PartTimeout`, `DEFAULT_TIMEOUT` 120 s: gcsfs `requests_timeout` as an aiohttp `ClientTimeout` bounding the connection and each wait for data, so gcsfs requests a stalled answer again instead of failing the block (`gcs_timeout`; GCS answers stall now and then, 212 s once), no total, so large chunks are not cut; a GCS part's `storage_options.requests_timeout` is refused at load (a total, not retried by gcsfs); `requests` and `cdsapi` timeouts; botocore timeouts on S3 only when given; not for Copernicus Marine or Icechunk inputs), time-sliced right-exclusively (`ds.arcomake.time_sel`; a part with `static_time` is read at that stamp instead, without the time dimension: constant fields a source stores as series, ERA5's `z` and `lsm`), chunked as planned (below), merged with `join="exact"`, then the dataset's `postprocess` steps run. If `checkpointing.step` is smaller than the interval, sub-intervals are written to a temp Zarr and re-opened lazily, to bound memory on HPC nodes. A dataset without the time dimension once processed (bathymetry, masks, fractions) is computed by a run's first block, in memory, and reused by the others (`download.RunStatic`); appends write only variables with time, so a run that does not write the first block (`--resume`) compares its static variables (and static coordinates other than indexes, e.g. cell bounds) with the stored ones and fails if they differ. All datasets are then merged (`join="exact"`, `combine_attrs="identical"`), the global `postprocess` runs, and `write_output` commits the first interval with `mode="w"` and appends later ones along `time_dim`, one commit each. The output is an Icechunk repository (`unpack` and zip outputs were removed with the move to Zarr v3).

**Part configs** (`DatasetPartConfig` in `dataset_utils.py`) are a plain Pydantic union of per-engine models. Every part takes `rename` (names changed right after opening) and `coordinate_tolerance` (index coordinates shared with an earlier part, of the same size, take that part's values if within the tolerance; parts are merged with `join="exact"`), e.g. GloFAS's drainage directions, whose `lat`/`lon` differ from the discharge's by 4e-12 (`PartAlignment`). The custom engines are xarray backend entrypoints in `backends.py`, registered through `[project.entry-points."xarray.backends"]` in `pyproject.toml`: `copernicusmarine`, `netcdfoverhttp`, `earlywarningdatastore`. For `copernicusmarine` and `earlywarningdatastore`, `start_datetime`/`end_datetime` are injected per interval. The EWDS backend makes one request per year of the interval, its months x its days (the service gives every valid date of that product; days outside the interval are dropped): the EWDS runs a user's requests one at a time, about two minutes apart (logbook, 18 Nov). The service's cost estimate is asked first (`_accepted`): a request it refuses (above 500 fields, days x variables; months not published yet) becomes one exact request per month. It leaves out unpublished days of a valid request: a block missing days fails, naming them. `copernicusmarine` is upstream main pinned at a commit (`f66a8b8`, for `COPERNICUSMARINE_MAX_POOL_CONNECTIONS`, not yet released): move to the first release that has it. The backend passes `chunk_size_limit=False` (undocumented: the toolbox then returns lazily indexed arrays, not Dask arrays of its own chunking, so the planned chunks decide the reads; unchunked, a variable is read in one piece); `tests/live` checks it by calling the backend directly, so run the live checks after any toolbox update. Since upstream #534 (in the pinned commit, not in 2.5.1) the toolbox refuses coordinates in `variables` (e.g. `depth`): ask for a data variable that has the coordinate and drop it (logbook, 17 Nov); the live checks do not cover this. The backend imports the toolbox at first use: it reads the pool size at import, and xarray imports every backend module whenever it lists engines. Unless set, `COPERNICUSMARINE_MAX_POOL_CONNECTIONS` is then Dask's thread count, at least 10 (`chunk_plan.dask_threads`): with the toolbox's 10 for 32 threads, connections were dropped and opened again all the time, and computing a block took 37 % longer (logbook, 18 Nov).

**Chunk planner** (`chunk_plan.py`, group 8): download recipes give no chunk sizes (part `chunks`, `chunk` steps and regrid `output_chunks` are refused at load: `dataset_utils.refuse_chunk_steps`, `DatasetConfig._no_part_chunks`; `process` keeps them, `[read] chunks` stay). Each part of each block (or checkpointed sub-block) is chunked by `chunk_plan.plan` (pure): every dimension whole except time; above the target, outer dimensions not needed whole are split, then time grows in multiples of its unit. Steps declare `Needs` (`@step(needs=...)`, merged by `steps.needs_for` on the opened part): `regrid` whole lat/lon, `get_bottom` gathers depth (counts whole for its tasks), `resample` multiples of the steps per bin (fixed frequencies over evenly spaced stamps; `pd.to_timedelta("1MS")` is a millisecond, so `to_offset`). `Budget`: `--memory-limit`/`ARCOMAKE_MEMORY_LIMIT` or `distributed.system.MEMORY_LIMIT` (RAM, cgroup, rlimit) × `USABLE` 0.8 / (threads × `COPIES` 4); target = min(that, Dask `array.chunk-size`). Above a task's share: a warning; no room for one task: `PlanError`. Download recipes must give `[save] chunks` (`DownloadConfig._stored_layout`: otherwise the stored chunks would be the planned ones, machine-dependent). The plan is logged per dataset; `download --plan` prints the first block's chunks and stored chunks and exits (`_print_plan`: no output, nothing computed, checkpointed datasets planned over the whole block; sources are opened). Stored chunks or shards above a task's share are warned about (`chunk_plan.stored_warnings`: written whole by one task). The parts of a dataset are planned together, for the dataset's steps and the recipe's steps after merging (`later_steps`), preferring multiples of the sources' `preferred_chunks`; checkpoint writes align too. Writes in download pass `align_chunks=True` (xarray rechunks what straddles stored chunks, append-aware). Dask names come from the part's settings and interval (`token=`): lazy backend arrays are not tokenized. The recipes' `output_chunks` had no effect: xarray-regrid reads only the regridded dimensions' entries, and whole is its default.

**Processing steps** (`steps.py`, `processing_utils.py`, `xarray_accessors.py`): importing `arcomake` registers the `ds.arcomake` accessor. A recipe step `name` is either a function of `processing_utils.py` registered with `@step` (called as `fn(ds, **args)`) or one of the `xr.Dataset` methods in `steps.DATASET_METHODS`; registered functions win (`sel`, `isel`, `transpose`, `astype`). `ProcessingStepConfig` (extra keys = arguments) checks the name, unknown/missing arguments and argument types **when the recipe is loaded**, so typos fail before any download. Download and process recipes may name their regrid grids once in `[grids.NAME]` (`grid = "NAME"` in a step; `dataset_utils.inline_grids` substitutes them before validation). Steps added in group 9: `sin_cos` (an angle as two components, before regridding and means), `coverage_attrs` (ACDD extent attributes from the coordinates; in download the time coverage is the whole output's, recomputed for each block from the stored stamps and the block's, `download._with_output_coverage`, since xarray replaces attributes on append and a checkpointed dataset carries its last sub-block's). Cell geometry for published cell measures: `cell_bounds` (CF bounds: horizontal midway between centres, clipped at the poles, as conservative regridding assumes; depth from layer thicknesses) and `cell_area` (m2 on a sphere of a given radius; volumes with `products`). To add a step: write a pure function `def name(ds: xr.Dataset, ...) -> xr.Dataset` with typed parameters, decorate it with `@step`, and add it to `STEPS` in `tests/test_steps_purity.py` (a test fails otherwise). Steps never modify their input (intent 1, tested for every step).

**Climatology** (`climatology.py`): with `split_dims`, `compute-climatology` computes one series (variable × index of the split dims) at a time: per-bin Welford statistics streamed in blocks of about 1 GB (numba kernel), the window in NumPy over point bands, each series written into its region of outputs whose metadata are written first. Without it, everything is one Dask graph (`_compute_climatology`); the two agree (tested).

**Checks** (`checks.py`): `ds.arcomake.validate(ChecksConfig)` runs the functions in `checks.CHECKS`, one per field of `ChecksConfig`; they raise `checks.ValidationError` on failure. `ensure_no_nans` counts missing values per time step for all variables in one Dask computation (it looped over every day; `_report_by_time`): everywhere, or inside a variable's masks, read as `mask > threshold` (`>=` with `inclusive`; boolean masks and fractions alike, NaN outside), 2D fields against a mask's first level; with `exact` (true, or a list of masks), values outside are failures too; a static variable under a time-varying mask is refused (e.g. the ocean variables exactly where `seafrac > 0`; it absorbed `fraction_domain`). A listed mask or variable missing from the dataset is a failure. `attributes` checks required attributes on every data variable (`long_name`, `units` by default) and distinct values (`long_name`), cheap. Download recipes may give `[checks]`, run on each block before its commit (`download._checked_block`): the time check over the block (dates from the recipe), the coordinate check, and `checks.guard_no_nans` (the `ensure_no_nans` rule as pass-through `apply_ufunc` wrappers that raise `ValidationError` while the block is written: no second reading; the first failing chunk is reported); a failure leaves the block uncommitted and the run resumable (`[checks]` is out of the fingerprint). `validate --start/--end` set the time check's bounds, as given to `download`. All config models reject unknown keys, except `ProcessingStepConfig` (arguments) and `EnsureNoNansCheck` (mask name → list of variables).

**HDF5 lock** (`hdf5_lock.py`): netCDF-C and HDF5 are not thread-safe, and xarray locks reads of array values, not what it reads while opening a file: two blocks of `download --blocks 2` (since removed) opening the GloFAS static file at once failed or crashed; opens and Dask's threaded reads still meet. Every netCDF4/h5netcdf file is opened through `hdf5_lock.open_dataset` (by `open_input` and the `netcdfoverhttp` backend; the engine guessed if not given), which holds one reentrant process-wide lock during the open and gives it to xarray for the reads; it replaces xarray's own netCDF locks for these files (taking both could deadlock: xarray combines locks in arbitrary order), so it excludes only netCDF work done through it. A test fails if other code opens datasets with xarray directly (`xr.open_*` without a non-HDF5 engine literal, xarray's openers imported by name, its netCDF4/h5netcdf backends). A stalled remote open blocks the other blocks' netCDF reads, as a stalled read did. GRIB opens share another lock (`backends._GRIB_OPEN_LOCK`, N6); opens overlapping reads were checked safe on ecCodes 2.48 and 2.49.

**Retries** (`retries.py`): a block of `download` that fails with a transient error (`is_transient`: timeouts, connection errors, HTTP 408/425/429/5xx, botocore timeouts and throttling, also when raised from or grouped in another error) is redone by `with_retries` (recipe `[retries]`: `attempts`, `wait`, `max_wait`; doubling waits); others fail at once. Retries are per block, not per source: a block reads all its sources in one computation. The clients retry requests first (gcsfs 6 times, cdsapi up to 500, the Copernicus Marine toolbox 9).

**Dask setup** (`dask_utils.get_client`, a context manager): `--dask-setup` is one of `synchronous|threads|processes|mpi|localcluster`. `download` defaults to `threads` because the custom remote backends don't serialize to distributed workers. `process` and `compute-climatology` default to `mpi` (dask-mpi under SLURM). `mpi` and `localcluster` read extra kwargs from Dask env config (`DASK_MPI__*`, `DASK_LOCALCLUSTER__*`) via `get_dask_env_options`. Optional `frisky` (from the `experimental` extra) can wrap the client.

**User settings** (`settings.py`): `ArcoMakeSettings` (pydantic-settings) reads the environment, then the dotenv file `~/.arcomakerc` (or `$ARCOMAKE_RC`; empty disables it); the `cli` group exports the values the environment lacks, because the libraries read only the environment (`TMPDIR`, `AWS_PROFILE`/`AWS_DEFAULT_PROFILE`, Copernicus Marine and CDS/EWDS credentials, `COPERNICUSMARINE_MAX_POOL_CONNECTIONS`; `DASK_*` keys go to Dask). Runs with `s3://` paths or Copernicus Marine parts fail at once if botocore's profile (`AWS_DEFAULT_PROFILE` first, then `AWS_PROFILE`) is not configured (`cli_utils.check_aws_profile`, also in the path checks of arguments). Errors name variables, never values (`settings.SettingsError`). Secrets are `SecretStr`; unknown keys are ignored with a warning naming the key. To support a new setting, add a field with the variable as `validation_alias`. Such files hold secrets: never read a real one; tests point `ARCOMAKE_RC` at temporary files (an autouse fixture disables it, except for live checks).

**Temp storage** (`temporary_utils.TempDirectoryRegistry`): a context-var-scoped registry of temp dirs, cleaned up on exit, atexit and signals, with stale-dir detection by PID. Checkpoints and remote downloads use it heavily, so `TMPDIR` should point to disk, not RAM. `cached_file(key, name, fetch)` fetches a file once per registry (one run): NetCDF files over HTTP (e.g. the GloFAS static file) are downloaded once, not once per block.

**Icechunk outputs**: every output is an Icechunk repository (`icechunk_utils`: storages from paths, botocore credentials for S3 because icechunk's own AWS client cannot read some profiles, region: the recipe's, else the bucket's as S3 reports it at the endpoint, else the profile's; the output check builds the storage first, so unusable paths and options fail before any download). `dataset_utils.write_output` = `prepare_for_writing` (the `[save]` layout as encodings) + one commit in a run (see below); `download` commits each block (message `download [start, end)`), `process` once, `compute-climatology` once per output: the graph path writes both outputs in one computation into their sessions with local schedulers (`write_outputs_together`; icechunk merges the writes of one session at a time, so on a distributed client each output is written, and computed, in turn), the `split_dims` path keeps one session per output and commits after the last series; both outputs are promoted only after both are written, with the same run label. Inputs: `engine = "icechunk"` (`backends.Icechunk`, explicit: no detection). Every run writes on its own branch (`icechunk_utils.Run`: `run/<label>`, label = command and start time, also in each commit's metadata); `Run.finish` moves `main` to the run's tip only if `main` is still where the run started (`reset_branch(..., from_snapshot_id=...)`, else `PromotionError`, branch kept), deletes the branch and applies the recipe's retention (`[save] keep_history` or `keep_versions`, `icechunk_utils.Retention`: `keep_history` counts from when a version was replaced, `keep_versions` reads `main`'s history only as far as needed; expire snapshots, then, if any were expired, garbage-collect objects older than the limit and `GRACE` (7 days, so another run writing to the same repository keeps its uncommitted chunks), with other runs' branches older than both; errors only logged). A failed run leaves `main` untouched. `download --resume` continues the newest failed download run (`icechunk_utils.waiting_run`: its branch, the blocks committed, read from commit metadata `arcomake_block`, and the recipe fingerprint `arcomake_recipe`, which must match; `recipe_fingerprint` leaves out what only changes reading: `[retries]`, parts' `timeout`, `checkpointing`); a plain rerun refuses while such a run can still be promoted. Blocks are written one at a time (`_write_block`); `--blocks N`, which ran blocks at once in threads with staging, was removed: a block twice as long is faster with less memory (logbook, 18 Nov). `--replace` (was `--overwrite`) is needed to write an existing repository and refused for anything that is not one (`cli_utils.check_destination`). No consolidated metadata (`[save] consolidated` removed). Checkpoints stay plain Zarr v3.

**Zarr v3**: checkpoints are plain Zarr format 3 stores (`dataset_utils._write_zarr`); there is no support for writing format 2. Sources in either format are read. Recipes give compressors as Zarr v3 codec metadata, `compressors = [{name = "blosc", configuration = {...}}]` (`CodecConfig`, built when the recipe is loaded). Codecs inherited from format 2 sources (numcodecs objects in the encodings) are dropped before writing (`_without_zarr2_codecs`): zarr 3 cannot write them in format 3. xarray stores a float `_FillValue` base64-encoded in format 3, apart from the array's own fill value. `[save] shards` (same form as `chunks`, `_resolve_sizes`) group whole chunks per object; without them outputs are unsharded (maintainer's decision); shards must be multiples of chunks (checked at load wherever both sizes are explicit, `_explicit_size_pairs`; whole dimensions before writing) and xarray refuses Dask chunks straddling shards; shards read from a source are dropped when `[save] chunks` changes the layout. With `split_dims`, shards along the split dimensions are 1, like chunks. `[save] shard_order` (`sharding.py`) orders the chunks inside shards (zarr's Morton by default; lexicographic puts a time step's levels together): zarr does not store the order in the metadata and builds the codec of an opened array with its default, so `write_order` selects an ordered subclass through zarr's codec registry (`codecs.sharding_indexed`) while writing, and arrays created by a write get their metadata first (`creates_arrays`) so their values go into opened arrays too; checked by reading shard indexes (`tests/test_shard_order.py`). Arrays pickled to distributed workers keep the order (zarr pickles it with the codec). `[save.encoding.VAR]` is merged key by key into the variable's encoding after `[save]` (never passed as xarray's `encoding=`, which replaces a variable's whole encoding); appended blocks reuse the stored encodings. An empty compressor list read from a source is dropped (outputs are compressed unless the recipe says `compressors = []`). zarr 3 refuses `storage_options` for local stores (plain paths, `file://`): Zarr inputs take them through `dataset_utils.storage_options_for`. `.zip` outputs are refused (`check_destination`, `write_output`).

## Working rules (from the maintainer)

- **Local notes:** machine-specific paths, host names and file names live in `CLAUDE.local.md` (gitignored, not committed). Keep them out of committed files, this one and `docs/logbook.md` included.
- **Secrets:** a credentials file on the project machine (named in `CLAUDE.local.md`) holds credentials. Never read, print or copy it. Source it only in the shell of the command that needs it (`set -a; . FILE; set +a`), without `set -x`, `env` or `printenv`. Commit files by name (never `git add -A`) and read `git diff --cached --stat` first. Logs may contain tokens: keep them out of the repo and read them through redacting filters.
- **Commits:** one purpose each; tests pass after each; a fix comes with its test; a commit that changes output for an unchanged recipe starts with `output:`. Nothing specific to ARCO-OCEAN or to a cluster goes into arco-make.
- **Real-data baseline:** a directory outside the repo (location and scripts in `CLAUDE.local.md`) holds the frozen code per commit (from `git archive`, each with its own venv), outputs per window, logs with `/usr/bin/time -v`, and a pinned copy of the 0.25° levels-50 recipe. "Same output" is checked bit for bit, metadata and encodings included. Runs use the image's eccodes 2.48 (via `ECCODES_DIR` and `ECCODES_DEFINITION_PATH`): older host eccodes cannot read GloFAS GRIB. Run a watchdog next to long runs: a hang (N7) sends no notification.
- **Experiments:** for distributed runs (`localcluster`/`mpi`), `--frisky` (the `experimental` extra) gives readable diagnostics. It is experimental and closed-source, so treat what it shows as a lead to confirm.

## Download performance (to revisit before a production download)

The maintainer will revisit performance after all planned changes, aiming at the shortest full download; details and figures in `docs/logbook.md` (16 Nov). In short, on the project VM:
- A full 0.25° levels-50 download took 166 h of running time and 7.8 days of calendar time (manual restarts, stalls), 46.6 s per day of data. The output resolution does not change the time: 10-level runs at 0.25°, 0.5° and 1.0° took the same.
- GLORYS 3D is about 75 % of the time. One process keeps 2–6 of 32 cores busy, and two processes each keep their speed: the limit is how the work of one process overlaps (its Dask graph), not CPU or network. A larger Copernicus Marine pool (32) cuts reading by about 20 % but processing by only about 5 %.
- Expected: about 6 days per resolution with group 7 with one-day blocks; long blocks are much faster (below).
- Group 8 (logbook, 18 Nov; 8-day window): long blocks are much faster (one 8-day block 8 min against 31-36 min in one-day blocks: per-block fixed costs, opening sources and EWDS queueing, static masks; more parallel work), memory grows with block length (44 GiB planned, 102 GiB with the old hand-set chunks); 256 MiB chunks (`DASK_ARRAY__CHUNK_SIZE`) were the fastest; checkpointing GLORYS per day halves memory but is 3.5x slower (avoid in production, maintainer). On a 32-day window (256 MiB chunks): 8-day blocks 32:47 at 49 GiB, 16-day 22:54 at 67 GiB, one 32-day block 15:43 at 63 GiB (memory levels off); two 16-day blocks at once (`--blocks 2`) 17:38 at 87 GiB, so `--blocks` was removed.
- Performance (logbook, 18 Nov, "performance"): production uses 32-day blocks (maintainer), computing about 25 s per day; the processor is mostly idle and Copernicus Marine reads dominate (58 % of task time; about 2 MB/s per connection, 58 ms round trips). The pool now follows Dask's threads (10 for 32 threads cost 37 % on an 8-day block); more threads, or a larger zarr executor (36 by default, where the toolbox runs its requests), made reads slower: keep 32 threads. No step is worth numba. EWDS runs a user's requests one at a time: one request per year of a block. Shards of 8 days x 50 levels: 116 objects instead of 7,193 per 32-day block, same time and memory.
- ERA5 stays on Google's GCS store (maintainer's decision). Two consecutive 600 s read timeouts on one baseline window (Feb–Mar 2020) remain unexplained; group 7's retries are the remedy. On 17 Nov such stalls hit most runs of window 2 (one or two per run, about 11 min each: timeout plus redone block, any day, also at the start of a process). Traced on 18 Nov: one GET now and then gets no answer for minutes, the connection pool never full; since then the timeout bounds silences and gcsfs retries the request (`gcs_timeout`), so a stall costs about 120 s, not a block (8 days: 5 stalls absorbed, no block redone). The GloFAS static file was fetched again in every block, so a server outage (502 on 16 Nov) failed the block it hit; it is now fetched once per run.

## Findings for Moby-Dick

A report for Moby-Dick (the consumer of ARCO-OCEAN) is due after the PRs are merged. Record every finding that affects consumers of the data here, and with details in `docs/logbook.md` (entries tagged **[Moby-Dick]**). So far:
- The published 0.25° dataset was downloaded with arco-make `6f0e2f1` (image of 30 Sep 2026), not `847b6f2`. Six pieces were rerun after network failures.
- N1 (uncompressed output without `[save] compressor`) and N2 (`astype` pitfalls) do not affect the published data: the arco-ocean recipes set lz4 and both `astype` arguments.
- N6 (EWDS requests of different months opened GRIB concurrently, which crashed ecCodes) can abort a download piece; it cannot write wrong data. Hypothesis, not checkable: some of the six rerun pieces of the 0.25° download failed this way.
- N7: a download can hang forever on a read from Google Cloud Storage (ERA5): gcsfs sends requests with no timeout by default (seen twice on the baseline). A killed piece leaves a partial store; it is safe only if rerun with `--overwrite`. Do not set `requests_timeout` in recipes run with code older than `f9fcd45` (N8). Since group 7, parts take `timeout` (seconds of silence; on GCS, gcsfs retries a stalled answer) and `requests_timeout` is refused on GCS parts.
- N8: a source chunk whose read fails with a timeout or connection error (any `OSError`) is read as NaN by zarr 2 `FSStore`, silently; a daily mean then averages the remaining hours and shows no NaN. Seen on real ERA5 data (two hours lost, bit-exact) and reproduced offline. Published ERA5 days may be means over fewer than 24 hours wherever a connection error outlasted gcsfs's retries; only recomputation from the source can tell. Fixed for Zarr inputs in `f9fcd45` (`dataset_utils.strict_zarr_store`, used by `open_input` and `open_archive`).
- N9: the Copernicus Marine fork's Zarr store turns any S3 error response into a missing chunk (NaN) after 9 retries (about 8.5 min). Code reading only; fix belongs in the fork. Exposes every Copernicus Marine variable to the same silent loss under a long outage. Since the move to zarr 3, the toolbox uses its zarr 3 store, which reads only 403 and 404 answers as missing chunks and raises other errors after its 9 retries (code reading): published data were read with zarr 2.
- N10: `[save] chunks = -1` over Dask chunks smaller than the dimension wrote overlapping chunks concurrently and lost most values, silently (since before `847b6f2`; fixed: such a write now fails). ARCO-OCEAN is not affected: its recipes make `lat` and `lon` whole Dask chunks before saving. Other users of arco-make might be.
- C10, checked 17 Nov: ERA5 daily accumulations (`tp`, `ssrd`, `strd`) cover [D-1 23:00, D 23:00), one hour early (ERA5 hourly accumulations end at their stamp); all other variables cover day D, midnight to midnight UTC. GloFAS `dis24` (v5 `time_mean`) is not one day off. Corrected (maintainer's decision): the arco-ocean ERA5 accumulation parts take `time_offset = "-1h"`; the windows differ by up to 8-12 % of the field's maximum (tp, ssrd).
- Outputs are now Icechunk repositories (versions, one commit per download block). Reading from S3 they open in under a second and read about 3× faster than plain Zarr v3 in our measurement, but requests stall now and then for icechunk's stream timeout (60 s by default): consumers should set a shorter `network_stream_timeout_seconds` (arco-make uses 20 s).
- Peak memory of the 0.25° levels-50 download: 36–53 GB for 2–5 days on 32 threads.
- Coarsening (logbook, 19 Nov; `docs/coarsen-ocean-datasets.md`): the published 0.25 deg dataset's sea rule (regridded depth below the level centre) misplaces water by layer, its bottom-value fill drew from far above, its sea-ice thickness and velocity were averaged with open water as 0, its `dis24` kept 1.7 % of the discharge reaching the coast (none of the Amazon's), and level 49 (never computed by NEMO) was published. The new recipes publish `seafrac` (any water), 49 levels, gaps filled from above, `siconc`/`sivol`/`usic`/`vsic` over the sea part, `dis24_outlets`, no WAVERYS. Note for Moby-Dick: weigh losses and volumes by `seafrac` x layer thickness x area.
- Attributes (logbook, 20 Nov): the recipes kept GLORYS12's `valid_min`/`valid_max` of its packed int16 values on `thetao`, `so`, `uo`, `vo`, `zos` (thetao: -32766 to 21306, meaningless on floats) and `cell_methods = "area: mean"` (the values are means over the sea part); the published dataset probably carries them (not checked). The new recipes publish `areacello` and `volcello` (areas on GLORYS12's sphere, R = 6,378,100 m) and name them in `cell_measures`.
- B6, measured on synthetic data: a missing year biases the anomaly variance of its bin low (6 % with 1 of 5 years missing). An all-NaN bin spreads NaN to its window neighbours. Fixed in group 6, with Feb 29 in Feb 28's bin (`bins = "day_of_year"`) and a `reference_period` setting (arco-ocean: 1993–2018): the climatology and anomaly_std have to be recomputed.
